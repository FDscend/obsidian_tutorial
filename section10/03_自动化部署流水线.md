# 自动化部署流水线

## 学习目标

- 理解 GitHub Actions 的基本概念
- 掌握三分支策略的同步机制
- 学会配置 GitHub Pages

## 前置条件

- 完成 [02\_配置与本地构建](02_配置与本地构建.md)

## 1. 三分支策略回顾

```
main ── 日常编辑笔记
  │
  ▼  sync-main-to-v5.yml
v5 ──── Quartz 构建环境
  │
  ▼  deploy.yml
gh-pages ── 静态文件 → GitHub Pages
```

### 为什么用三个分支？

| 方案       | 优点                          | 缺点                                                     |
| ---------- | ----------------------------- | -------------------------------------------------------- |
| 单分支     | 简单                          | 仓库混入构建工具文件，Obsidian 中看到 `node_modules/` 等 |
| **三分支** | main 保持纯净，构建和发布分离 | 需要同步机制（用 Actions 解决）                          |

## 2. 部署工作流（deploy.yml）

监听 `v5` 分支推送，自动构建并部署。

```yaml
name: Build and Deploy to GitHub Pages
on:
  push:
    branches: [v5]
# ...
jobs:
  build-and-deploy:
    steps:
      - uses: actions/checkout@v4
        with:
          persist-credentials: false
      - uses: actions/setup-node@v4
        with:
          node-version: 22
      - run: npm ci
      - run: npx quartz plugin install
      - run: npx quartz build
      - uses: peaceiris/actions-gh-pages@v4
        with:
          github_token: ${{ secrets.PERSONAL_TOKEN }}
          publish_dir: ./public
          publish_branch: gh-pages
```

> 使用 `peaceiris/actions-gh-pages` 而非 `actions/deploy-pages`，因为前者不受 GitHub Pages 环境保护规则限制。

### 受保护的 `gh-pages` 分支如何自动更新？

如果 `gh-pages` 启用了 **Require a pull request before merging**，默认的 `GITHUB_TOKEN`（`github-actions[bot]`）不能直接推送。解决方式是：

1. 使用仓库管理员账号创建 **Classic PAT**，勾选 `repo` scope；
2. 在仓库 **Settings → Secrets and variables → Actions** 中保存为 `PERSONAL_TOKEN`；
3. 在保护 `gh-pages` 的 ruleset 的 **Bypass list** 中，为 `Repository admin` 选择 **Always allow**；
4. 将 `PERSONAL_TOKEN` 传给 `peaceiris/actions-gh-pages` 的 `github_token`。

PAT 代表创建它的管理员账号，而不是一个可单独添加到 bypass 列表的机器人账号。因此无需、也不能通过添加 `github-actions[bot]` 来获得绕过权限。

### 为什么不直接用 `actions/deploy-pages`？

GitHub 官方的 `deploy-pages` 需要 `github-pages` 环境，且默认有分支保护规则，导致 `v5` 分支无法部署。`peaceiris/actions-gh-pages` 直接将构建产物推送到 `gh-pages` 分支，绕过环境限制。

## 3. 同步工作流（sync-main-to-v5.yml）

监听 `main` 分支推送，自动将内容同步到 `v5` 分支的 `content/` 目录。

```yaml
name: Sync main → v5
on:
  push:
    branches: [main]
# ...
jobs:
  sync:
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
          persist-credentials: false
      - uses: actions/checkout@v4
        with:
          ref: v5
          path: v5-branch
          persist-credentials: false
      - name: Sync content
        run: |
          for dir in section0 section1 ... appendix image; do
            rsync -a --delete "$dir/" "v5-branch/content/$dir/"
          done
          cp markdown格式总结.md v5-branch/content/ 2>/dev/null || true
      - name: Commit and push
        env:
          PERSONAL_TOKEN: ${{ secrets.PERSONAL_TOKEN }}
        run: |
          cd v5-branch
          git add content/
          git commit -m "sync: 从 main 同步内容更新"
          git push "https://x-access-token:${PERSONAL_TOKEN}@github.com/${GITHUB_REPOSITORY}.git" HEAD:v5
```

### 受保护的 `v5` 分支如何自动同步？

`v5` 同样可以保留 PR 规则，做法与 `gh-pages` 一致：让管理员账号位于 ruleset 的 **Always allow** bypass 列表中，并用 `PERSONAL_TOKEN` 推送 `v5`。

这里有一个容易忽略的问题：`actions/checkout` 默认会把 `GITHUB_TOKEN` 写入仓库的 Git 配置。即使 `git push` 的 URL 中写了 PAT，该已保存的认证 header 仍可能优先被使用，最终以 `github-actions[bot]` 身份推送并收到 `GH013`。

因此，两个 checkout 都必须设置 `persist-credentials: false`，再使用带 `PERSONAL_TOKEN` 的推送 URL。这样实际鉴权身份才是有 bypass 权限的管理员账号。

### 同步范围

| 目录/文件                 | 同步？ | 说明         |
| ------------------------- | :----: | ------------ |
| `section0/` ~ `section9/` |   ✅   | 教程章节     |
| `appendix/`               |   ✅   | 附录         |
| `image/`                  |   ✅   | 图片资源     |
| `markdown格式总结.md`     |   ✅   | 根目录的笔记 |
| `README.md`               |   ✅   | 仓库说明     |
| `Clippings/`              |   ❌   | 网页剪藏     |
| `template/`               |   ❌   | 笔记模板     |
| `.doc/`                   |   ❌   | 内部文档     |

## 4. GitHub Pages 设置

Actions 配置好后，还需要在 GitHub 上完成 Pages 设置：

1. 打开仓库 → **Settings** → **Pages**
2. **Source** 选择 **Deploy from a branch**
3. **Branch** 选择 `gh-pages`，目录 `/ (root)`
4. 点击 **Save**

> 如果 `gh-pages` 分支还没有（Actions 第一次运行后才生成），可以先选 `None` 保存，等 Actions 跑完再回来设置。

## 5. 完整发布流程

```bash
# 1. 编辑笔记（在 main 分支）
git add .
git commit -m "更新笔记"
git push origin main

# 2. 等待 Actions 自动执行
#    sync-main-to-v5.yml → deploy.yml

# 3. 访问网站
#    https://用户名.github.io/仓库名/
```

两次推送之间约 2-3 分钟网站更新。直接修改并推送 `v5`（例如更新 `quartz.config.yaml`）也会触发同一部署工作流。

## 常见问题

### Q: Actions 报错 "Branch not allowed to deploy"？

使用 `peaceiris/actions-gh-pages` 替代 `actions/deploy-pages`，或在仓库 Settings → Environments 中删除 `github-pages` 环境。

### Q: 同步工作流没有触发？

确认工作流文件在 `main` 分支的 `.github/workflows/` 目录下，且 `.gitignore` 没有忽略 `.github/workflows/`。

### Q: 工作流报 `GH013: Changes must be made through a pull request`？

按以下顺序检查：

1. 打开错误日志给出的 `rules?ref=...` 链接，确认目标分支只命中了预期的 ruleset；
2. 确认该 ruleset 的 `Repository admin` bypass 是 **Always allow**，而不是 **For pull requests only**；
3. 确认 `PERSONAL_TOKEN` 是管理员账号创建的 Classic PAT，并有 `repo` scope；
4. 确认执行 Git 推送前的每个 `actions/checkout` 都设置了 `persist-credentials: false`；
5. 确认推送命令或部署 action 实际传入了 `PERSONAL_TOKEN`，而不是默认 `GITHUB_TOKEN`。

### Q: 网站访问 404？

- 确认 Actions 已完成（绿色勾号）
- 确认 Pages 设置中选择了 `gh-pages` 分支
- 硬刷新浏览器（Ctrl+F5）
